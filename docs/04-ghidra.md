# Ghidra и C167 для этой прошивки

## Поправка к прежней редакции

Ранее здесь было сказано, что связываться с Ghidra не стоит из-за отсутствия
поддержки C166/C167. Уточнение: в штатной поставке Ghidra процессорного
модуля для C166 действительно нет, но **рабочие сторонние модули существуют**,
и если у вас такой уже есть — Ghidra полностью пригодна для этой задачи.
Дальше — как настроить её именно под FBH3ID60.

## Карта памяти (установлена по таблице контрольных сумм)

Это не догадка: таблица сумм по адресу `0x1FC00` хранит границы регионов в
адресах процессора, и они однозначно дают привязку.

| Параметр | Значение |
|---|---|
| База флеша | `0x800000` |
| Смещение в файле | `адрес - 0x800000` |
| Размер образа | `0x80000` (512 КБ) |
| Код | примерно с `0x810000` (файл `0x10000`) |
| Калибровки | `0x810000`–`0x81BFFF` вперемешку с кодом |
| Таблица сумм | `0x81FC00` (файл `0x1FC00`) |

Регионы из таблицы сумм, покрывающие образ: `0x800000-0x803FFF`,
`0x804000-0x805FFF`, `0x808000-0x80BFFF`, `0x80C000-0x80FBFF`,
`0x810000-0x813FFF`, `0x814000-0x817E67`, `0x818190-0x81BFFF`,
`0x81C000-0x81FFFF` и далее до `0x87FFFF`.

Обратите внимание на пропуск `0x817E68`–`0x81818F`: этот участок намеренно
исключён из подсчёта сумм. Там лежит блок идентификации (строка
`0261208504 1037368793 ... FBH3ID60 ...` по адресу `0x818182`, файл `0x10182`)
и цепочка осей перед ней.

## Загрузка образа

- **Format**: Raw Binary
- **Language**: C166/C167 из вашего плагина, порядок байт **little-endian**
- **Base Address**: `0x800000` — тогда адреса в Ghidra совпадут с адресами
  из таблицы сумм. Если поставить `0`, всё поедет на 8 МБ, и сверяться с
  нашими отчётами будет неудобно.

Наши инструменты печатают **смещения в файле**. Скрипт импорта прибавляет
базу образа сам, так что при базе `0x800000` метки встанут правильно.

## Импорт разметки

```bash
./analyze.sh                     # получить out/FBH3ID60_maps.json
```

В Ghidra: **Window → Script Manager**, добавить каталог `tools/ghidra`,
запустить `ImportMaps.py`, указать `out/FBH3ID60_maps.json`.

Скрипт понимает оба формата, которые встречаются в этой прошивке:

- **с заголовком** (`bosch_header`) — размечает байты `nx`/`ny`, массивы
  осей и тело карты по отдельности;
- **голая сетка** (`bare_grid`) — размечает только тело; осей в блоке нет,
  они общие и лежат в цепочках по адресам `0x1008C` и `0x181C1`.

Для каждой карты создаются метка, закладка в категории `Kennfeld` и
комментарий с размерностью и происхождением.

## Что искать в коде

Разметка карт уже сделана без дизассемблера. Ghidra нужна для двух вещей,
которые структурным анализом не берутся:

1. **Оси трёх карт зажигания.** Карты `0x10529` (11x16), `0x10A01` (12x15)
   и `0x10AB5` (12x16) лежат голыми сетками, их оси общие и хранятся
   отдельно. Ни одна из 45 найденных осей не имеет 11 точек, так что
   привязку даст только чтение кода. Ссылки на карты уже найдены:

   | Карта | Ссылки в коде (смещение в файле) |
   |---|---|
   | `0x10529` | `0x3B60E`, `0x536EF`, `0x53A73` |
   | `0x10A01` | `0x3D7B7`, `0x3D88D`, `0x3D935`, `0x4590D`, `0x45D4D` |
   | `0x10AB5` | прямых 16-битных ссылок не найдено |

   Ищите функцию интерполяции: она получает указатели на ось X, ось Y и
   тело карты. Соседние аргументы в точке вызова и будут адресами осей.

2. **Масштабы пересчёта.** Смотрите, на что умножается результат
   интерполяции. Для карт зажигания практика уже подтверждает множитель
   `0.75 °/ед.` (см. `docs/05-находки.md`), но код даст точный ответ.

Для поиска ссылок можно пользоваться и нашим грубым инструментом:

```python
python3 -c "
import sys; sys.path.insert(0,'tools'); import fwlib
fw = fwlib.load('firmware/FBH3ID60_stok.bin')
print([hex(h) for h in fwlib.find_le16_refs(fw, 0x0529)])"
```

Он ищет 16-битное смещение внутри сегмента (для области карт это
`адрес & 0xFFFF`), что для C167 с адресацией через `DPP` работает как
дешёвая первая прикидка. Точный результат — только за дизассемблером.

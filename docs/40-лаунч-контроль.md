# Лаунч-контроль (2-step): разбор ограничителя и врезка

Задача владельца: лаунча в стоке нет, дописать его кодом. Условие --
скорость около нуля (`0x881D`, 1.25 км/ч на единицу) и газ выше порога;
тогда низкий предел оборотов с отсечкой подачи. Предложено было врезаться
в ограничитель, туда, где читается `NMAX` (0x14BB4).

Сделано, но **врезка стоит не на чтении `NMAX`, а на шаг дальше по той же
цепочке** -- там, где прошивка решает «отключить подачу на всех
цилиндрах». Ниже разбор, почему: в этой калибровке штатный ограничитель
подачу не отключает, и низкий `NMAX` дал бы удержание оборотов зажиганием,
а не отсечку.

```
python3 tools/launch.py apply  firmware/FBH3ID60_v2M.bin -o out/v2M_lc.bin
python3 tools/launch.py show   out/v2M_lc.bin
python3 tools/launch.py set    out/v2M_lc.bin -o out/v2M_lc2.bin --nmax 4500
python3 tools/launch.py remove out/v2M_lc.bin -o out/v2M_back.bin
python3 tests/test_launch.py
```

Готовый файл: `firmware/FBH3ID60_v2M_lc.bin` -- v2M плюс лаунч с
параметрами по умолчанию, суммы пересчитаны, проверка 32 из 32.

## Как устроен штатный ограничитель

Всё ниже -- одна задача 10 мс (список вызовов 0x8304D8..): сначала
ограничитель 0x83BE6E, потом сведение моментов 0x83B304, потом решение об
отключении подачи 0x83C0A4. Шаг 10 мс виден по счётчику `TNMAXDV`: он
прибавляет единицу за вызов, а в дамосе записан в единицах 10 мс.

### 1. Выбор предела, 0x83BE6E

```
если 0xFD08.2          предел = NMXDKPU  (0x14BB8, 1200)   дроссель неизвестен
иначе если 0xFD08.1    предел = NMXDAEF(0x881C) * 40        запасной режим ЭДЗ
иначе
    обороты > NMAXDV дольше TNMAXDV и 0xB37C.0  -> 0x915C.0
    предел = 0x915C.0 ? NMAXDV (0x14BB6) : NMAX (0x14BB4)
0x9158 = предел
```

Биты `0xFD08.1` и `0xFD08.2` в образе только сбрасываются (0x82F63C), а
кривая `NMXDAEF` (0x105EB) вся из нулей: это ветки для электронной
дроссельной заслонки, которой на этой машине нет. `0xB37C.0` --
неисправность датчика скорости (её же ставит диагностика 0x82FCB2), по ней
штатно включается `NMAXDV`.

### 2. Жёсткая ветвь, 0x83BF2E

```
если обороты > предел + DNMAXH:
    0xFD16.2 = 1, 0xFD16.1 = 1, 0x9154 = 0        (момент от ограничителя -- ноль)
```

### 3. Мягкая ветвь -- ПИ-регулятор по моменту

Ошибка `предел - прогноз оборотов` (прогноз = обороты + градиент x `TNMXPR`;
у всех известных прошивок `TNMXPR` = 0, то есть прогноза нет), П-часть
`NMAXPRL`, И-часть `ZINMAXRL`, результат -- допустимый момент 0x9154,
сверху ограничен `MDIMX`. Без вмешательства 0x9154 = `MDIMX` << 8.

### 4. Сведение моментов, 0x83B304

`0x9154` идёт в минимум с 0x9122, 0x9176, 0x9118, снизу подпирается
0x8F12, результат -- 0xF7D6, итоговый допустимый момент.

### 5. Решение об отключении подачи, 0x83C0A4

```
0xFD16.5 = (0xFD0E.6 и 0xFD18.14)                  отключение на выбеге
        или (0xFD18.14 и не 0xFD02.6 и не 0xFD16.4)
        или 0xFD6E.5                                отсечка по перегреву
если 0xFD16.5:   0x8874 = 4                         все четыре цилиндра
иначе:           ступень снижения по моменту 0x8873 (0..4);
                 отключать цилиндры, только если ступень >= REDZEM (0x8875)
```

`0xFD18.14` -- выбег (считается в 0x83E718: дроссель закрыт `0xFD48.10`,
полоса оборотов `DNSAH`/`DNSAL` с гистерезисом, скорость, задержки),
`0xFD6E.5` -- отсечка по перегреву по `NOVH`/`DNOVH` (функция 0x86145E).

### 6. От 0x8874 до форсунок -- целиком во флеше

```
0x854CA2  0x8874 -> 0x8A24; при 0x8A24 > 0 автомат 0x9868: 0 -> 3
0x854E56  состояние 3: 0x8A20 = таблица[0x11916 + фаза*8 + (0x8A24-1)] & 0x0F
0x854F8A  0x8A21 = 0x9869 ? 0xFF : 0x8A20           маска гашения цилиндров
0x8416F0  0xFD8A = 0x8A21                           (единственная запись 0xFD8A)
0x841946  если 0xFD8A.0: CC30 = T7-1, цилиндр пропущен  (впрыск отменён)
          иначе: время впрыска 0x987A, CC30 заряжается, канал включается
          так же 0xFD8A.1 -> CC29, .2 -> CC28, .3 -> CC23
```

Таблица шаблонов 0x11916 во всех FBH3ID60 -- **сплошь 0xFF**. Значит,
любое ненулевое 0x8874 гасит сразу все четыре цилиндра, частичного
отключения в этой калибровке нет вообще. Когда 0x8874 возвращается к нулю,
состояние 3 -> 4 обнуляет маску сразу (0x854D36), впрыск возвращается со
следующего цикла. На всём пути -- от 0x83C0A4 до регистров CAPCOM -- **нет
ни одного вызова во внутреннее ПЗУ процессора**. Этим же путём работает
отсечка на выбеге: если на машине при сбросе газа в передаче лямбда падает
в ноль, путь проверен самой машиной.

## Почему не в NMAX

Если понизить предел в п. 1, ограничитель будет держать низкие обороты
своими средствами. А средства у него такие:

* **Отключение цилиндров по моменту выключено калибровкой.**
  `REDZEM` (0x183DE, «threshold between ignition intervention and injector
  disabling») = 5 при любой температуре ОЖ. Ступень 0x8873 считается как
  `(0x9160 + гистерезис) / 1000`, где 0x9160 -- снижение в тысячных долях
  четырёх цилиндров (0..3999), а гистерезис `REDHYOC`/`REDHYUC` x 20 =
  500/600. Выходит не больше 4, и условие «ступень >= 5» не выполняется.
  Оговорка: сложение делает `0x006852`, а она во внутреннем ПЗУ. По 35
  другим её вызовам (половина значения плюс знаковая поправка, затем
  проверка на 0x7FFF) это сложение с насыщением; при любом другом
  разумном смысле ступень выходит ещё меньше. Но формально без ПЗУ это не
  доказать.
* **Жёсткая ветвь ставит `0xFD16.2` и `0xFD16.1`.** `0xFD16.2` в образе
  никто не читает (ни битовой командой, ни словом, ни в сыром просмотре
  байт). `0xFD16.1` читается -- как разрешение того самого отключения по
  моменту (0x83C1E6), которое перекрыто `REDZEM`.
* Остаётся момент 0x9154 -> 0xF7D6, и дальше зажигание: по 0x83E2AA угол
  считается иначе, как только 0xF7D6 отличается от 0x9778. Цепочку
  вмешательства зажиганием я до конца не прослеживал.

То есть по коду, который есть в дампе, штатный ограничитель на этой
калибровке обороты держит **поздним зажиганием**, а не отсечкой. Оговорка:
дамп -- полный образ внешней флешки, но 32 КБ внутреннего ПЗУ процессора
в нём нет (ниже, «Что есть в дампе»), и что там делают `0x006852` и
прочие, видно только по вызовам. Отсечку через `NMAX` по дампу доказать
нельзя, а через `0xFD16.5` -- можно, и до самых форсунок (п. 6).

Держать на старте 4000+ оборотов поздним зажиганием при полностью
открытом дросселе -- это горячий выпуск и катализатор. Поэтому лаунч
сделан отсечкой подачи.

### Поправка про DNMAXH

В docs/13 и в профиле было записано «топливо возвращается на `NMAX` минус
120». Неверно: `0x0067d8` складывает. Видно по двум другим её вызовам:

| где | аргументы | смысл |
|---|---|---|
| 0x83BF76 | прогноз, обороты 0xF8A0 | прогноз оборотов = обороты + приращение |
| 0x83C0F4 | порог 0x915E, `MDHYEZ` << 8 | порог с гистерезисом «torque-hysteresis for decision cylinder fuel cut-off» |

С вычитанием в обоих местах выходила бы бессмыслица (отрицательные обороты,
гистерезис не в ту сторону). Байтовая сестра `0x0067e6` так же
складывает `NOVH + DNOVH` в отсечке по перегреву. Значит жёсткая ветвь
ограничителя срабатывает на `NMAX + DNMAXH`, а `NMAX` -- уставка мягкого
регулятора.

## Куда врезано

Решение п. 5, последнее условие -- перегрев:

```
            было                                 стало
83C116  8A 37 01 50  jb   0xfd6e.5, 83C11C   DA 86 00 FC  calls 0x86FC00
83C11A  0D 02        jmpr cc_UC, 83C120      2D 02        jmpr  cc_EQ, 83C120
83C11C  6F 88        bset 0xff10.6           (не тронуто: «отключить»)
83C120  6E 88        bclr 0xff10.6           (не тронуто: «не отключать»)
83C122  4A 88 0B 65  bmov 0xfd16.5, 0xff10.6
```

На 0x83C11A никто не прыгает, поэтому две команды заменяются вместе.
Подпрограмма возвращает решение во флаге Z (`rets` флаги не трогает), и
первым делом проверяет тот же перегрев, так что стоковое поведение
сохраняется. Подпрограмма -- в пустом хвосте сегмента 0x86:

```
86FC00  jb    0xfd6e.5, CUT        ; перегрев -- как было
86FC04  mov   r4, 0xb37c
86FC08  jb    r4.0, NOCUT          ; неисправен датчик скорости -- лаунча нет
86FC0C  mov   r4, 0xb304
86FC10  jb    r4.0, NOCUT          ; неисправен датчик дросселя -- лаунча нет
86FC14  movb  RL4, 0x881d
86FC18  cmpb  RL4, LCVMAX
86FC1C  jmpr  cc_UGT, NOCUT        ; скорость выше порога
86FC1E  movb  RL4, 0x89f3
86FC22  cmpb  RL4, LCWDKMN
86FC26  jmpr  cc_C, NOCUT          ; газ ниже порога
86FC28  movb  RL4, 0x8ab4
86FC2C  cmpb  RL4, LCTMOTMN
86FC30  jmpr  cc_C, NOCUT          ; мотор холодный
86FC32  mov   r4, LCNMAX
86FC36  jnb   0xfd16.5, CMP        ; подача сейчас есть -- порог LCNMAX
86FC3A  sub   r4, LCDNH            ; подача отключена -- порог ниже на LCDNH
86FC3E  jmpr  cc_C, NOCUT
86FC40  cmp   r4, 0xf8a0
86FC44  jmpr  cc_C, CUT            ; обороты выше порога
86FC46  mov   r4, #0  ; rets       ; Z=1 -- не отключать
86FC4A  mov   r4, #1  ; rets       ; Z=0 -- отключить
```

Гистерезис держится на прошлом значении `0xFD16.5`: ячейка ОЗУ не нужна,
и выделять её наугад не пришлось. Подпрограмма меняет только `r4` -- в
точке врезки он рабочий и дальше перезаписывается раньше, чем читается.
Все кодировки команд взяты из стокового кода этой же прошивки.

## Параметры

Лежат в пустом хвосте калибровок, на той же странице DPP1, что и `NMAX`
(0x14BB4 читается как 0x4BB4, параметры -- как 0x7000..0x7006). Область
0x1699A..0x17E67 пуста во всех FBH3ID60 и входит в регион суммы
0x14000..0x17E67.

| адрес | имя | формат | по умолчанию | смысл |
|---|---|---|---|---|
| 0x17000 | `LCNMAX` | u16, x0.25 об/мин | 4200 | выше -- подача отключается |
| 0x17002 | `LCDNH` | u16, x0.25 об/мин | 200 | подача вернётся ниже `LCNMAX - LCDNH` |
| 0x17004 | `LCVMAX` | u8, x1.25 км/ч | 2.5 | скорость `0x881D` не выше |
| 0x17005 | `LCWDKMN` | u8, x0.390625 % | 69.9 | дроссель `0x89F3` не ниже |
| 0x17006 | `LCTMOTMN` | u8, x0.75 - 48 °C | 60 | ОЖ `0x8AB4` не ниже |

В WinOLS их можно завести руками по этой таблице; `launch.py set` меняет
их и пересчитывает суммы. Выключить лаунч, не убирая код, -- поставить
`LCNMAX` выше `NMAX`.

Почему такие умолчания:

* **4200 / 4000.** Диагностика датчика скорости (ниже) считает отсечку
  на скорости до 20 км/ч в окне 1520..4000 об/мин неисправностью ДС. С
  порогами 4200/4000 отсечка идёт целиком выше окна.
* **2.5 км/ч.** `0x881D` -- это сырая скорость / 160 с округлением вниз,
  показание 2 значит «меньше 3.75». При трогании порог проходится за доли
  секунды.
* **70 % дросселя.** Сток признаёт полную нагрузку с 65 % (`WDKVLN`,
  docs/33). Ниже 40 % `launch.py` предупреждает: лаунч сработает при
  обычном трогании.
* **60 °C.** Не долбить отсечкой холодный мотор.

## Что видит остальная прошивка

`0xFD16.5` -- общий признак «подача отключена», его читает 41 команда
по всей прошивке. По дамосу отсечку учитывают задержка
лямбда-регулирования (`IMLSALR`), диагностика пропусков (`RLSALUN`),
нейтрализация катализатора (`TSAKAMN`), адаптация давления (`KISA`);
какая из 41 команды чья, я не разбирал. Читатели `0xFD16.5` при лаунче
видят то же, что при выбеге, -- и это правильно: подача действительно
отключена. А вот `0xFD18.14` (сам выбег) лаунч не ставит, поэтому то, что
читает его напрямую, ведёт себя иначе: фильтры перехода момента
0x9182/0x9184 и 0x925A/0x925C, биты 0xFD1A.0 и 0xFD14.12, таймер модели
плёнки 0x9974.0 (плёнка всё равно сбрасывается по `0xFD54.9`, 0x857070).
Маску гашения 0x8A20 читает и контур детонации (0x84EC76, 0x84F25C) --
погашенные цилиндры он пропускает. Последствия, о которых надо знать:

* **Диагностика датчика скорости, 0x82FCB2.** Ветка 1: ОЖ выше 64.5 °C,
  скорость ниже 20 км/ч, обороты 1520..4000, `0xFD16.5` -- и так 50 раз
  подряд -> неисправность ДС. Счётчик сбрасывается, как только подача
  вернулась, а при отскоках отсечка длится десятки миллисекунд. С
  умолчаниями 4200/4000 окно не задевается вовсе. Ветка 2 (скорость ниже
  3.75, обороты выше 3000, нагрузка выше 50 %) -- стоковая и от лаунча не
  зависит; на отсечке она прерывается, потому что автомат форсунок
  гасит `0xFD54.9` (0x854CE4).
* **Возврат подачи.** После отсечки прошивка возвращает момент через
  фильтр перехода (0x83C224 выбирает постоянную по `0xFD16.5`), как после
  выбега. Отскоки от лаунча поэтому могут быть мягче, чем у голой
  отсечки.
* **Неисправный датчик скорости.** Пока неисправность не опознана,
  скорость читается нулём, и на ходу при газе выше 70 % обороты упрутся в
  4200. Опознаёт её штатная диагностика (на выбеге), после этого
  `0xB37C.0` выключает лаунч. Это и есть плата за лаунч без датчика
  сцепления.

## Чем проверено

`tests/test_launch.py`:

* **опора в коде** -- 12 проверок по стоковому образу: что `0xFD16.5`
  ведёт к 0x8874 = 4, что `0xFD6E.5` -- перегрев, что `0x881D` = скорость /
  160, что `0xB37C.0` и `0xB304.0` -- неисправности ДС и дросселя, что
  `REDZEM` = 5, что `0xFD16.2` никто не читает, что `0x0067d8` складывает;
* **до форсунок** -- 9 проверок: автомат, таблица 0x11916 из 0xFF во всех
  FBH3ID60, единственная запись 0xFD8A, отмена событий CAPCOM по всем
  четырём битам, ни одного вызова в ПЗУ на этом пути;
* **флешка и ПЗУ** -- 4 проверки: заголовок 0x808000, `SYSCON.ROMEN` в
  стартовом коде, одинаковые записи сумм ПЗУ у Kia и ВАЗ, все 124
  процедуры в 0x0000..0x7FFF;
* **байты** -- подпрограмму и врезку разбирает дизассемблер из
  `c166.sinc` (тот, что сходится с Ghidra 40 из 40), текст сверяется
  построчно;
* **поведение** -- маленький исполнитель C166 на ровно эти команды
  (на любой другой падает) проходит путь от 0x83C116 через вызов до
  развилки. 9000 случайных и граничных входов при трёх наборах параметров
  против модели на Python -- совпадение полное. На скорости выше порога
  решение совпадает со стоком на 2000 входах. Отсечка на развёртке
  оборотов: с 4210 вверх, подача вернулась на 4000 вниз;
* **образы** -- ставится на все 16 FBH3ID60 из `firmware/`, на B103eq09
  отказывается; до пересчёта сумм меняются только 6 + 78 + 7 байт; суммы
  32 из 32; `remove` возвращает исходник байт в байт.

Чего тесты не доказывают: что ЭБУ примет правленую **кодовую** область.
Суммы по всем 32 регионам сходятся, но правка кода в этом проекте первая.
Исходный файл и программатор держать под рукой.

## Как проверять на машине

1. Залить `FBH3ID60_v2M_lc.bin`, оригинал сохранить. Завести, дать
   прогреться выше 60 °C. Стереть ошибки.
2. **Стоя, нейтраль.** Перегазовка частичным газом до 3000 -- ничего не
   меняется. Газ в пол -- обороты упираются в ~4200 и прыгают
   4000..4200.
3. Газ в пол на холодном моторе (ниже 60 °C) -- лаунча нет, штатная
   отсечка.
4. **На ходу** выше 5 км/ч газ в пол на первой -- обороты идут до
   штатной отсечки, не до 4200.
5. Старт: газ в пол стоя, обороты на 4200, отпустить сцепление.
6. После каждой серии читать ошибки. Появится P0500 (датчик скорости) --
   сообщить: значит ветка диагностики засчитала лаунч, порог надо
   поднимать.

## Что есть в дампе и чего нет

Дамп -- **полный образ внешней флешки** AM29F400, 512 КБ. Первые 64 КБ
прочитаны, а не пропущены: суммы Bosch на 0x800000..0x80FBFF сходятся,
сектора 0x800000..0x805FFF и 0x80C000..0x80FBFF пусты и в заводском
образе (их эталонные суммы -- суммы сплошных 0xFF), а в 0x808000 лежит
заголовок программы с точкой входа 0x833012 и подпись `C3 3C` в конце
сектора. Прежняя запись в docs/22 «загрузочный сектор не читается»
неверна.

Но 124 процедуры, которые код зовёт по 0x0700..0x7F7A (1676 вызовов),
лежат **не во флешке**, а во внутреннем ПЗУ процессора C167
(0x0000..0x7FFF, 32 КБ):

* стартовый код 0x833012 первым делом пишет `SYSCON`, сохраняя бит
  `ROMEN` -- включение внутреннего ПЗУ; `ROMS1` = 0, то есть ПЗУ стоит в
  сегменте 0, там, куда идут вызовы;
* в таблице сумм Bosch есть две записи на 0x00000000..0x00007FFF с
  суммами 0x0FA0F5CF и 0x0F4716B3 -- это не пустая память (пустая дала бы
  0x1FFFE000). Проверка сумм (0x86B20C) сверяет их только при `ROMEN` = 1;
* процедура записи во флешку вызывается как `calls 0x0057F6` -- из той же
  флешки, которую она стирает, она работать не может;
* **у ВАЗовского B103EQ09** (0261207832, LADA 1.5 8V) суммы ПЗУ те же
  самые. То есть ПЗУ у ВАЗовского и у Kia M7.9.7 одно.

BSL-загрузчики (Combiloader, ChipLoader и т. п.) читают внешнюю флешку и
EEPROM, внутреннее ПЗУ процессора они не читают. Поэтому его нет ни в
одном выложенном дампе M7.9.7, кто бы и как его ни снимал.

## Как получить 100 %

1. **Путь лаунча уже прослежен до форсунок** (п. 6) -- без ПЗУ. Это тот
   же путь, что у отсечки на выбеге.
2. **Проверка на машине, без которой 100 % не бывает:**
   * лямбда (OBD PID 0x14) во время отскоков падает к 0.05..0.1 В --
     подача отключена; при позднем зажигании она бы осталась около 0.8;
   * пробник на разъём форсунки (лампа или осциллограф) -- самое
     прямое: на отсечке импульсов нет;
   * лог ОЗУ, если блок отвечает на KWP2000 `ReadMemoryByAddress` (0x23):
     0x00FD16 бит 5, 0x380874, 0x00FD8A. Поддержку 0x23 на M7.9.7 никто
     не подтвердил, проверять запросом.
3. **Закрыть вопрос с ПЗУ полностью** -- прочитать его через BSL.
   Открытый C167BootTool/ME7BootTool (`-readInt 0x8000`) ставит
   `SYSCON.ROMEN` = 1, `ROMS1` = 1 и читает 32 КБ с 0x010000. Если ПЗУ
   защищено (заводская опция C167), вместо кода придёт `9B 00 9B 00 ...`
   -- проверить по первым 16 байтам. Подлинность прочитанного проверяется
   суммами Bosch: 0x0FA0F5CF по первой половине и 0x0F4716B3 по второй,
   16-битные слова. Годится любой ВАЗовский M7.9.7 на C167 (не M7.9.7+,
   там ST10). С ПЗУ разбор становится полным: смысл `0x006852`, `0x0067d8`,
   проверка сумм, стартовый код.

## Альтернатива, которую я не стал ставить

«Мягкий» лаунч -- подмена предела на 0x83BF26 (`mov r4, 0x4bb4` ->
`calls`, 4 байта). Ограничитель тогда держал бы низкие обороты своим
ПИ-регулятором, то есть поздним зажиганием. По причинам выше это не то,

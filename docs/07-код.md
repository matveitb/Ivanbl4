# Разбор кода: что удалось вытащить дизассемблером

## Про Ghidra

Запустить Ghidra в этой среде не вышло: сама Ghidra 12.1.2 сюда не скачивается
(доступ к github.com закрыт политикой сессии, доступен только ваш репозиторий).
Но присланный модуль оказался полезнее, чем просто плагин — в нём лежит
`data/languages/c166.sinc`: **машиночитаемая Sleigh-спецификация системы
команд C166** плюс эталонные тесты дизассемблирования.

Поэтому вместо запуска Ghidra написан `tools/c166dis.py` — дизассемблер C166,
таблица инструкций которого **порождается из этого же `c166.sinc`**, а не
пишется по памяти. 201 конструктор, все опкоды и длины из спецификации.

Проверка: `python3 tests/test_c166dis.py` прогоняет эталонные векторы из
`tests/headless/cases/*/expected.disasm` того же модуля (их сгенерировала
настоящая Ghidra). Совпадение **40 из 40, 100 %**.

Строки, которые Ghidra выдала как данные (`.byte`), исключены из подсчёта:
они получены её анализом таблиц переходов, а не дизассемблированием.

## Как вызывается интерполяция карт

Обращение к калибровочной таблице выглядит единообразно:

```
83E3D2  E6 FC F5 09  mov   r12, #0x9f5      ; тело карты  (файл 0x109F5 = KFZW)
83E3D6  E6 FD 57 01  mov   r13, #0x157      ; ось         (файл 0x10157)
83E3DA  F2 FE 96 90  mov   r14, 0x9096      ; входная величина
83E3DE  F2 FF A2 90  mov   r15, 0x90a2      ; входная величина
83E3E2  DA 00 B8 78  calls 0x0078b8         ; процедура интерполяции
83E3E6  F7 F8 9D 88  movb  0x889d, RL4      ; результат в ОЗУ
```

Смещения 16-битные, к ним прибавляется база сегмента калибровок `0x10000`.

`tools/mapxref.py` линейно дизассемблирует кодовую область, копит
непосредственные загрузки в r12..r15 и на каждом вызове снимает их значения.
Получается **1323 места вызова** и **44 подпрограммы**, к которым сходятся
указатели на калибровки — это и есть процедуры интерполяции.

Сами процедуры (`0x0078b8`, `0x0077b6`, `0x00716a` и другие) лежат в
**сегменте 0, которого нет в этом дампе**: по этим смещениям в файле стоят
`0xFF`. Это согласуется с таблицей контрольных сумм, где есть записи на
регионы `0x00000000`–`0x00007FFF` — память вне образа.

## Оси карт зажигания — вопрос закрыт

Раньше ось нагрузки для `KFZWOP` найти не удавалось: среди 45 байтовых осей
нет ни одной на 11 точек. Причина выяснилась из кода — **эта ось
шестнадцатибитная, и счётчик у неё тоже хранится словом**, поэтому байтовый
поиск её пропускал.

| Ось | Адрес | Точек | Разр. | Множитель | Значения | Для карт |
|---|---|---|---|---|---|---|
| нагрузка | `0x10157` | 12 | u8 | 0.75 % | 9.8 … 99.8 % | `KFZW`, `KFZW2`, `KFZWMS` |
| нагрузка | `0x14B70` | 11 | u16 | 0.0234375 % | 10, 15, 20, 25, 30, 40, 50, 60, 70, 80, 100 % | `KFZWOP` |
| обороты | `0x10103` | 16 | u8 | 40 об/мин | 680 … 6520 | `KFZW`, `KFZW2`, `KFZWMS` |
| обороты | `0x100F2` | 16 | u8 | 40 об/мин | 440 … 6520 | `KFZWOP` |

Все четыре строго монотонны и дают физически осмысленные ряды — это и есть
проверка корректности.

## Цепочка формирования угла

```
83E3E2  calls 0x0078b8        ; интерполяция KFZW
83E3E6  movb  0x889d, RL4     ; сохранить базовый угол
83E3EA  movbs r9, RL4         ; знаковое расширение -- углы ЗНАКОВЫЕ
83E3EC  movbs r4, 0x8858 ; add r9, r4    ; += поправка 1
83E3F2  movbs r4, 0x8859 ; add r9, r4    ; += поправка 2
83E3F8  movbs r4, 0x889a ; add r9, r4    ; += поправка 3
83E3FE  cmp   r9, #0x7f                  ; ограничение сверху
```

То есть итог = базовый угол из `KFZW` плюс три аддитивные поправки.
`movbs` (знаковое расширение) подтверждает то, что говорил DAMOS:
значения карт зажигания знаковые.

## KFZWMS действительно работает ограничителем

`KFZWMS` интерполируется той же процедурой и по тем же осям, результат
ложится в ОЗУ `0x8898`. Дальше по адресу `0x3E232`:

```
83E232  movbs r8, 0x8897        ; ограничиваемая величина
83E23A  movbs r4, 0x8898        ; KFZWMS
83E242  sub   r8, r4            ; r9:r8 = 0x8897 - KFZWMS
83E246  movbs r4, 0x91cc ; add  ;        + поправка (сама ограничена 60)
83E252  cmp   r9, #0x0
83E254  jmpr  cc_SLT, 0x83e268  ; знаковое сравнение
...
83E25C  movb  RL4, 0x8898       ; больше предела -> взять KFZWMS
83E268  ...                     ; иначе -> взять исходную величину
        movb  0x8899, RL4
```

Это разворачивается в

```
0x8899 = min(0x8897 + 0x91CC, KFZWMS)
```

со знаковой арифметикой. Ограничитель **обходится**, если установлен бит
`0xFD42.8` или `0xFD42.11`.

**Что это значит.** Раньше я говорил, что `KFZWMS` похож на ограничитель, но
это было чтение названия из DAMOS. Теперь это видно в коде: `KFZWMS`
действительно является **верхней границей** для величины из `0x8897`.
Калибровщик поднял его на высоких нагрузках — значит, граница там ослаблена.

**Чего я не выяснил.** Что именно лежит в `0x8897` и в каких единицах, до
конца не прослежено. Пока это не сделано, я не берусь утверждать, что
ограничитель урезает именно откат по детонации, — доказано лишь то, что
`KFZWMS` ограничивает сверху некоторую величину ветви зажигания.

## Инструменты

```bash
# дизассемблировать участок
python3 tools/c166dis.py firmware/FBH3ID60_stok.bin --range 0x3E3D0 0x3E400 --raw

# найти карты и оси по ссылкам из кода
python3 tools/mapxref.py firmware/FBH3ID60_stok.bin --callees \
    --names out/xfer_FBH3ID60.json --axis-only
```

## Оговорка про массовый поиск

`mapxref.py` находит 434 адреса калибровок, на которые ссылается код. Это
заметно больше, чем даёт DAMOS, но **автоматическое сопоставление оси там
ненадёжно**: распознаватель принимает первое значение за счётчик и находит
«ось» там, где её нет. Поэтому в профиль внесены только оси карт зажигания,
проверенные вручную и по физическому смыслу значений. Остальной вывод
`mapxref` — материал для проверки, а не готовая разметка.

# Логгер: блок, а если есть — и ШДК, в один файл

Владелец снимает блок Car Scanner'ом. Для смеси по УДК — родному узкому
зонду — это годится, но Car Scanner опрашивает всё выбранное по кругу
поровну, и STFT с напряжением зонда достаются реже, чем могли бы. Логгер
спрашивает то, что нужно для расчёта, и так часто, как позволяет
K-линия, и пишет в том же формате. Если есть ШДК со своим контроллером,
он пишется в тот же файл по тем же часам — сводить два лога не нужно.

## Что нужно из железа

| что | годится | не годится |
|---|---|---|
| адаптер ELM327 | USB (CH340, FTDI); Bluetooth **классический** — после сопряжения в Windows виден как COM-порт; Wi-Fi (обычно 192.168.0.10:35000) | только Bluetooth LE (часть «iOS-совместимых»): COM-портом он не становится |
| ШДК — **не обязателен** | с последовательным выходом: Innovate LC-1, LC-2, LM-2, MTX-L, DLG-1 (ISP2, 19200) и почти все контроллеры, что продают у нас под ВАЗ — RUSC, MCE, самодельные: их делают «как LC-1», потому что только этот формат понимают программы вроде Online Tuner; AEM 30-4110 и X-Series 30-0300 (число строкой, 9600); PLX iMFD; Zeitronix ZT-2 | только стрелочный прибор или только аналоговый 0–5 В (без АЦП ноутбук его не прочитает); 14Point7 Spartan 3 (по порту у него только команды, лямбда — по CAN и аналогу); «быстрая» прошивка LC-1 для «Матрицы» (115200, другой формат) |
| ноутбук | Windows, редактор калибровок (.exe из Actions) | |

УДК — родной узкий зонд — отдельно подключать не надо: его напряжение
блок отдаёт сам, в PID 14, вместе со STFT.

**Классический Bluetooth-адаптер — спарить один раз.** В окне логгера
то же самое есть по кнопке «Как подключить?», там же кнопки, которые
открывают нужные окна Windows.

1. Адаптер — в разъём OBD, зажигание включить: адаптер питается от
   разъёма. Если он подключён к телефону (Car Scanner) — отключите там
   или выключите на телефоне Bluetooth: адаптер держит одно подключение.
2. **Windows 11:** «Параметры» → «Bluetooth и устройства» → «Добавить
   устройство» → «Bluetooth». Адаптера нет в списке — прокрутите
   найденные вниз, там ссылка показать все устройства (24H2 и новее); на
   сборках до 24H2 её нет, там «Bluetooth и устройства» → «Устройства» →
   «Обнаружение устройств Bluetooth» → «Дополнительно».
   **Windows 10:** «Параметры» → «Устройства» → «Bluetooth и другие
   устройства» → «Добавление Bluetooth или другого устройства» →
   «Bluetooth».
3. Адаптер обычно зовётся OBDII, OBD2, OBD-II или V-LINK; у Vgate iCar
   Pro два имени — нужен «Android-Vlink», а «IOS-Vlink» — Bluetooth LE без
   COM-порта. PIN — 1234, не подошёл — 0000, потом 6789; некоторые просят
   только «Подключиться». Дальше он «Сопряжено» — это нормально:
   подключится, когда программа откроет порт.

Windows заводит адаптеру COM-порт сама, но называет его безлико —
«Стандартный последовательный порт по соединению Bluetooth (COM5)», и
таких порта бывает два: исходящий (компьютер подключается к адаптеру —
он и нужен) и входящий (для ELM327 бесполезен: открывается, но ответа
никогда не будет). Логгер различает их сам — по коду устройства (`hwid`,
`BTHENUM\{00001101-…}`: у исходящего в конце адрес адаптера, у входящего
нули) — и подписывает: «COM5 · Bluetooth «OBDII» · исходящий». Имя
берётся из реестра (`HKLM\SYSTEM\CurrentControlSet\Services\BTHPORT\
Parameters\Devices\<адрес>\Name`, читается без прав администратора).
Кнопка «Найти адаптер» перебирает порты и сама выбирает тот, где
отвечает ELM327; входящие не трогает.

Если порта «исходящий» нет: «Win+R» → `rundll32.exe
shell32.dll,Control_RunDLL bthprops.cpl,,2` (или кнопка «COM-порты
Bluetooth» в подсказке; из «Параметров» — на Windows 11 «Bluetooth и
устройства» → «Устройства» → «Дополнительные параметры Bluetooth», на
Windows 10 «Другие параметры Bluetooth», вкладка «COM-порты») →
«Добавить...» → «Исходящий» → «Обзор...» → адаптер → «ОК». Проверить
направление можно и в «Диспетчере устройств»: «Порты (COM и LPT)» →
свойства порта → «Сведения» → «Путь к экземпляру устройства» — адрес в
конце вместо нулей значит исходящий. Адаптер «для iPhone» (только Bluetooth LE) COM-порта не
создаёт вовсе — с ноутбуком он не заработает.

USB-адаптер виден как «COM3 · USB-SERIAL CH340» и т. п., ШДК через
USB-переходник на RS-232/TTL — так же.

## Как снимать

1. Редактор → открыть прошивку, которая сейчас в машине (нужна, чтобы
   прямо в езде видеть цель и ошибку).
2. «Инструменты → Снять лог».
3. «Подключение» — строка «COMn · Bluetooth «OBDII» · исходящий» (или
   USB, Wi-Fi); не уверены — «Найти адаптер». «Скорость порта» —
   «подобрать», «Протокол» — «сам (ATSP0)». «ШДК, если есть» → «Порт» —
   «нет: смесь по УДК (родной зонд)»; если ШДК есть — его порт и
   протокол, не знаешь протокол — начни с ISP2.
4. «Подключить и писать». Сначала поднимается K-линия — это несколько
   секунд, — потом оживают приборы: обороты, расход, дроссель, УДК в
   вольтах (тёплый фон — бедно), STFT, LTFT, ошибка воздуха, контур.
5. Ехать: мотор прогрет, третья передача, газ в пол от 1500 до отсечки,
   между разгонами накат с закрытым дросселем; для частичных — ровные
   участки по нескольку секунд. Таблица «Узлы ДМРВ: набрано» показывает,
   где данных уже хватает и где STFT в упоре.
6. «Стоп» → «Открыть в расчёте»: лог уже в окне «Смесь по УДК».

Файл пишется построчно, сразу на диск (по умолчанию
`Документы/udk_logs/лог_дата_время.csv`), в том же формате, что у Car
Scanner. Если программа упадёт или ноутбук сядет, снятое не пропадёт, а
сам файл читается любым разбором, который понимает Car Scanner.

Из командной строки то же самое:

```
python3 -m editor.cli log --elm list
python3 -m editor.cli log --elm auto
python3 -m editor.cli log --elm COM5
python3 -m editor.cli log --elm COM3 --wb COM4 --wb-proto isp2
python3 -m editor.cli log --elm wifi:192.168.0.10:35000 --wb COM4 --wb-proto ascii
```

`list` — показать порты с подписями, `auto` — найти адаптер и писать. Без
`--wb` — без ШДК, смесь потом считается по УДК и коррекциям.

## Что блок отдаёт — по коду

Всё ниже найдено в коде и перепроверено независимо; на машине ещё не
проверено.

### Две двери на K-линии

У блока две сессии, и какая откроется, решает способ инициализации:

| инициализация | протокол ELM | сессия | что в ней |
|---|---|---|---|
| медленная, 5 бод, адрес 0x33 (ключ `08 08`) | **3** — ISO 9141-2 | OBD (`0x836DA6`) | режим 01, **режим 22** |
| быстрая (импульс 25 мс) | **5** — KWP2000 | заводская (`0x8366DA`, ключ `EF 8F`) | режим 01, **чтение памяти 0x23**; на режим 22 — отказ `7F 22 12` |

Автопоиск ELM (`ATSP0`) пробует ISO 9141 раньше KWP, так что обычно
попадает в первую. Логгер это проверяет сам: если ELM попал в KWP, а
память там не читается, — переподключается по ISO 9141 ради режима 22.
Если выбрать протокол руками, логгер его не меняет.

Двигатель подписывается в ответах адресом **0x17** (так в прошивке:
`0x8366C0`, `0x836DFA`), а не 0x10, как у многих. Логгер адрес не
угадывает: двигатель — тот, кто в ответе на `0100` объявляет расход
воздуха; у коробки его нет.

### Режим 01

Обработчик — `0x864996`, таблица переходов на `0x1297A`. На `0100` блок
отвечает `BE 1F B8 11`, на `0120` — `80 00 00 00`:

| PID | что | ячейка | пересчёт |
|---|---|---|---|
| 0x03 | контур: 1 ждёт, 2 замкнут, 4 разомкнут (цель ≠ 1.000, сброс топлива, нагрузка), 8 авария | `0x8939` | `0x84B818` |
| 0x05 | ОЖ | `0x8AAF` | ×0.75 − 48 |
| 0x06 / 0x07 | STFT / LTFT | старший байт `0x95AE` / `0x9850` | 0x8000 = 0 % |
| 0x0C | обороты | `0xF8A0` | ×4 |
| 0x10 | расход | `0xF868` | floor(ml ÷ 9) × 25: шаг **0.25 г/с** и всегда вниз, в среднем на 0.4 кг/ч — логгер прибавляет середину ступеньки; `FFFF` — упор |
| 0x11 | дроссель | `0x89F3` | тот же байт, что сравнивается с `WDKVLN` |

Неподдержанные PID блок молча пропускает — ELM ждёт таймаута и пишет
`NO DATA`. Поэтому логгер спрашивает только то, что блок назвал в `0100`.

PID 03 = 2 — ещё не доказательство замкнутого контура: при части условий
байт `0x8939` хранит прошлое значение. Надёжный признак — DID 1216.

### Режим 22 (ISO 9141)

Обработчик `0x8656D6`: запрос `22 12 XX`, ответ `62 12 XX данные`,
неизвестный XX — молчание. Через него блок отдаёт то, чего в режиме 01
нет или оно огрублено:

| DID | что | ячейка |
|---|---|---|
| 1235 | **сырой АЦП ДМРВ**, 10 бит — номер точки `HFM_LIN` × 2 | `0x903C` |
| 1285 | расход в полном разрешении, 0.1 кг/ч | `0xF868` |
| 1283 | наполнение rl, 0.0234375 % | `0xF870` |
| 1216 | бит 1 — регулятор по зонду работает | `0xFD3A.14` |

АЦП ДМРВ — главное. Блок берёт тарировку как `HFM_LIN[АЦП >> 1]`, без
интерполяции (`0x842C2A`), и с АЦП поправка ложится ровно в ту точку,
где датчик врёт, а не ищется обратно по расходу, который блок уже
умножил на поправку пульсаций. На модели с картой пульсаций до +13 %
расхождение с заложенной ошибкой 1.3 % против 2.9 %.

### Чтение памяти (KWP)

В заводской сессии есть `0x23` (обработчик `0x8382E8`): запрос
`23 AA AA AA LL`, ответ `63 данные`. В самом обработчике ключа нет —
только длина запроса и класс адреса; класс 1 — внешнее ОЗУ
0x380000–0x387FFF, то есть данные 0x8000–0xBFFF. Пропустит ли запрос
диспетчер, который живёт в сегменте 0 (его в дампе нет), — не видно,
поэтому логгер пробует при подключении. Если пустит — это лучшее, что
можно снять: **заданная лямбда** (`0x9818`, адрес `38 18 18`) и АЦП ДМРВ
(`0x903C`, `38 10 3C`). Тогда расчёт берёт цель из блока, а не из модели
прошивки — с защитой компонентов и переходами.

(В прошлой редакции здесь стояло, что `0x23` закрыто проверкой доступа
`0xE1CA == 5`. Это неверно: `0xE1CA` — длина запроса, «5» значит только
«23 AA AA AA LL».)

## Замкнутый контур на полном газе

По коду (`0x84BB04`) регулятор по зонду выключает не полная нагрузка, а
цель, **не равная 1.000** (цель от 0.9985 до 1.0012 блок округляет до
ровно 1.000), сброс топлива, нагрузка выше 99.75 % или принудительное
обогащение (`0xFD3A.9`, условия не разобраны до конца). У v2M цель на
полном газе 1.000 — значит регулятор, скорее всего, работает и там, и
STFT доливает. Тогда бедный УДК при полном газе значит одно: STFT
упёрся в предел (+25 %, `0x15DD6`) и дальше доливать некуда. Логгер
пишет и STFT с напряжением УДК, и состояние контура (DID 1216, а без
режима 22 — PID 03), так что это будет видно на первом же разгоне.

На этом и стоит смесь по УДК: пока контур замкнут, ошибка воздуха —
(1 + STFT) × (1 + LTFT), а упор виден по STFT у предела при бедном
зонде (docs/40). С ШДК — лямбда ШДК × (1 + STFT) × (1 + LTFT) / цель:
неважно, кто закрыл ошибку, ШДК её видит или коррекция.

## Как опрашивается блок

По K-линии ELM успевает 6–7 запросов в секунду на всех. Делить их
поровну — значит снимать температуру ОЖ так же часто, как обороты.
Поэтому план опроса неравный. Если режим 22 отвечает:

| что | как часто |
|---|---|
| АЦП ДМРВ (DID 1235), обороты, дроссель | каждый круг |
| УДК и STFT (PID 14, одним ответом) | каждый круг; с ШДК — через круг |
| расход 0.1 кг/ч (DID 1285) | через круг |
| регулятор по зонду (DID 1216) | раз в 4 круга |
| LTFT | раз в 8 кругов |
| ОЖ | раз в 20 кругов |

Если нет — то же по PID режима 01: обороты, расход, дроссель, УДК со
STFT каждый круг, контур (PID 03) раз в 4. Без ШДК STFT — это и есть
измерение, поэтому каждый круг; с ШДК мерит он, и чаще достаются
обороты и дроссель. Если блок не отдаёт PID 14, STFT берётся из PID 06.

PID 14 по коду (`0x864C6E`): первый байт — `0x88CE`, напряжение УДК
(5 мВ на единицу по стандарту; пересчёт из АЦП `0x8901` делает функция
сегмента 0, её в дампе нет), второй — та же ячейка STFT `0x95AE`, что и
в PID 06. PID 15 — второй зонд, после катализатора, второй байт `FF`.

На имитаторе с задержкой K-линии 110 мс это 2–2.3 раза в секунду для
главных величин — против примерно одного раза у Car Scanner'а, который
опрашивает все параметры по кругу поровну.

Заголовки ответов включены (`ATH1`): на функциональный запрос может
ответить и коробка-автомат (адрес 18), и её «обороты» — не обороты
двигателя. Ответ берётся только от двигателя, а сумма в конце строки
проверяется. Если отвечают двое, число ответов в конце запроса не
шлётся — иначе ELM вернул бы первый, чужой.

Если ELM попал в KWP и чтение памяти работает, план другой: АЦП из
памяти каждый круг, заданная лямбда и расход (PID 10) через круг.

Метка показания — середина между запросом и ответом. Неподдержанные
блоком PID не спрашиваются вовсе (список берётся из ответа на 0100).

Порядок запросов внутри круга каждый раз перемешан. Регулятор по узкому
зонду качает STFT с периодом около секунды, круг опроса — тоже около
секунды, и при ровном порядке STFT читался бы раз за разом в одной фазе,
как стробоскопом: среднее врало бы, а ровный ноль походил бы на
разомкнутый контур.

Каждый запрос шлётся с числом ответов в конце (`010C1`): тогда ELM не
ждёт таймаута других блоков. Клоны, которые этого не понимают, отвечают
«?» — логгер это замечает и дальше шлёт без числа.

Правила ELM327, которые соблюдаются (datasheet ELM327DSK):

* писать только после `>`: любой байт, пришедший, пока адаптер занят,
  прерывает его — в том числе его собственный поиск протокола. Если
  ответ запоздал, логгер ждёт приглашения, а не шлёт следующую команду;
* пока адаптер пишет `SEARCHING...` или `BUS INIT`, он поднимает шину —
  ожидание продлевается до 20 с;
* `BUS INIT: ...ERROR`, `UNABLE TO CONNECT`, `LV RESET` распознаются до
  того, как служебный текст вычищается, и ведут к переподключению;
* скорость COM-порта подбирается мусорными байтами `7F 7F` с переводом
  строки, а не пустой строкой (на пустую ELM повторяет прошлую команду),
  и принимается, только если ответ кончается на `>`; порт при этом
  открывается один раз — Bluetooth при каждом открытии заново поднимает
  радиоканал;
* нулевые байты PIC-клонов вычищаются; молчаливый сброс адаптера
  (заголовки вдруг пропали) тоже ведёт к переподключению.

После `LV RESET`, потери шины, выключенного зажигания, обрыва Bluetooth
или Wi-Fi логгер сам переподключается — открывает порт заново — и пишет
дальше в тот же файл. То же с портом ШДК.

Bluetooth в Windows обрывается молча: порт остаётся открытым, байты
уходят, ответа нет, ошибки тоже. Поэтому молчание различается: блок
молчит («NO DATA», адаптер на месте) — ждём до 30 запросов, зажигание
могли выключить на минуту; молчит сам адаптер, даже без «>», — после
трёх таких запросов порт открывается заново (на имитаторе — через 15 с).
Открытие исходящего порта, когда адаптер выключен, Windows держит 5–13 с
и отвечает «превышен таймаут семафора» — это не поломка; а бывает, что
не отвечает вовсе. Поэтому и подключение, и «Найти адаптер» ждут порт не
дольше 25 и 20 с.

## Как читается ШДК

Контроллер шлёт показания сам, спрашивать его не надо. Разбор терпит
подключение посреди пакета и потерю байтов — ищет следующий заголовок.
В лог идёт только годная лямбда: прогрев датчика, калибровка в воздухе и
ошибки отсеиваются по состоянию, которое сообщает сам контроллер, а не
выдаются за «бедную смесь».

Форматы сверены с открытыми разборщиками (Tactrix, RomRaider, libISP2,
rusEFI, txlogger) и с настоящими пакетами из них:

* **ISP2.** Если в пакете несколько датчиков (LM-2 на два канала,
  DLG-1, цепочка LC-1), берётся первый — иначе два датчика перемешались
  бы в один канал. Множитель AFR вне 6…25 — слово битое, не «лямбда».
  LM-1 внутри цепочки тоже читается.
* **Текст.** Число должно стоять первым полем: строка «Board: VBatt 13.8»
  — не показание. Поля состояния AEM («Ready», «No-errors») проверяются.
  Двоичный мусор (выбран не тот протокол) отбрасывается. Режим «процент
  O2» на приборе AEM по числу от AFR не отличить — его надо выключить.
* **PLX.** Пакет, где после потери байта не кратно пяти, выбрасывается
  целиком: сдвинутые записи дают правдоподобную чужую лямбду. Второй
  модуль (номер 1) не подмешивается.

## Как проверено

Машины в проверке нет, поэтому собеседники — имитаторы
(`editor/core/fakecar.py`): ELM327 v1.5 с блоком за ним, который ведёт
себя как по коду (две двери, адрес 0x17, отказ `7F 22 12` в KWP,
молчание на неподдержанное, коробка, отвечающая первой, УДК и STFT в
PID 14), и ШДК, шлющий пакеты ISP2, PLX, ZT-2 или текст с лямбдой из
модели мотора с известной ошибкой ДМРВ. Сбои — по заказу: шина не поднялась, `LV RESET` посреди
записи, оборванный порт.

| что | результат |
|---|---|
| **без ШДК: УДК и STFT из PID 14 → расчёт по коррекциям** | **ошибка ДМРВ найдена с расхождением до 2.2 % (верхний узел; на частичных 0.5 %)** |
| с ШДК: логгер → файл → расчёт, по PID | ошибка ДМРВ найдена с расхождением до 1.3 % |
| то же с АЦП из режима 22 и картой пульсаций | 1.4 % (по расходу — 3.0 %) |
| KWP с чтением памяти: цель и АЦП из блока | 1.3 % |

| оборвался порт | открыт новый, запись продолжилась |

# Ghidra: как развёрнута и что дала

## Развёртывание

```
tools/ghidra/setup.sh [каталог]
```

Ghidra 12.1.3 (сборка 20260817), модуль C166 из `firmware/` ставится
правкой версии в `extension.properties` -- он собран под 12.1.2, но
проверок совместимости нет. Образ грузится как Raw Binary, процессор
`C166:LE:16:default`, cspec `tasking`, база 0x800000.

Две грабли, на которые стоит не наступать:

* **В Ghidra 12 убран Jython.** Headless-скрипт на Python падает с
  `JythonStubException`. Скрипты -- на Java либо под PyGhidra.
* Имя файла релиза угадывать бесполезно, версия и дата сборки не
  совпадают с версией модуля.

## Скрипты

| файл | что делает |
|---|---|
| `scripts/DecompileTargets.java` | дизассемблирует вокруг адресов, создаёт функции, выдаёт C |
| `scripts/InterpCalls.java` | ловит вызовы процедур интерполяции и собирает константы из r12..r15 |
| `scripts/MapInventory.java` | сплошная декомпиляция, частотный список подпрограмм |
| `gen_annotate.py` | генерирует `Annotate.py` со всей накопленной разметкой |

## Процедуры интерполяции

Найдены по частоте вызовов: **0x833A00** (77 вызовов), **0x833F10** (59),
**0x833FFC** (28), **0x834310** (9). Соглашение о вызове:

```
r12 = указатель на тело карты      r13 = страница тела
r14 = указатель на ось             r15 = страница оси
физический адрес = страница * 0x4000 + указатель
```

Страница 0x204 -> файл 0x10000, 0x205 -> 0x14000, 0x206 -> 0x18000,
0x207 -> 0x1C000.

## Что дал сплошной проход

`results/карты_по_коду.txt` -- **118 различных пар тело/ось**, каждая
подтверждена тем, что код реально вызывает с ней интерполяцию. Из них 16
уже были известны по имени, 102 были безымянными.

Расхождение с переносом DAMOS в районе 0x18xxx оказалось 0 или ±1 байт,
так что имена для них восстанавливаются почти однозначно. Среди полезного:

| адрес | имя | что |
|---|---|---|
| 0x18449 | `KFTVSA` | задержка отсечки топлива при сбросе, ось 0x100B3 |
| 0x18471 | `NWECVTM` | обороты возврата топлива |
| 0x18476 | `TVSATM` | задержка отсечки после пуска |
| 0x182F5…0x183A9 | `KFDMDFA` и соседи | фильтры момента, все шесть с осью 0x181DD |

## KFLF: вопрос закрыт

Пятая процедура есть -- **0x833BE0**, и она устроена иначе. Ей дают
указатель не на голое тело, а на **заголовок** классического бошевского
вида:

```
[nx][ny][ось X: nx байт][ось Y: ny байт][данные: nx*ny байт]
```

Поэтому поиск указателя #0x10EC ничего и не давал: указывают на
заголовок 0x190CE, а не на данные 0x190EC. По #0x10CE нашлась ровно одна
ссылка -- 0x8517C0, и она вплотную к чтению `FRKAP` 0x517DA, которое
было известно раньше. В нивовской прошивке ровно то же самое: заголовок
0x19180, указатель #0x1180, одна ссылка.

```
заголовок 0x190CE   nx=12  ny=16   данные 0x190EC, 192 байта
ось X  0x190D0  10 20 25 30 38 45 55 75 100 125 150 160
ось Y  0x190DC  11 21 28 36 40 45 54 62 67 71 80 89 97 107 116 125
```

**Поправка:** раньше я рисовал эту карту по осям 0x1821E и 0x181F7,
взятым по аналогии с `KFLBTS`. Неверно -- оси у неё свои, внутри
заголовка, и значения другие.

Функция целиком:

```c
void FUN_8517c0(void) {
  sVar3 = FUN_833be0(0x10ce, 0x206, DAT_00f89e, DAT_00f86b);   // KFLF
  uVar4 = func_0x006a60(sVar3 * DAT_8190cd, DAT_008829 + 0x180); // x FRKAP
  DAT_0089ff = uVar4 < 0x100 ? uVar4 : 0xff;
}
```

Отсюда два факта. `FRKAP` 0x190CD действительно множит значение альфы --
это теперь доказано, а не предположено. И у `KFLF` **нет никаких условий
применения**: функция линейная, ни маски, ни флагов, ни рампы, в отличие
от `KFLBTS`.

Процедурой 0x833BE0 опрашиваются 23 заголовочные карты, все разобраны в
описи -- с размерами и адресами данных.

## Плёночная модель найдена

Из описи видно четыре карты 7x9 с одинаковым шагом 0x3F, которые
вызываются одной функцией (0x8521D2..0x852470) процедурой 0x833FFC с
общей осью 0x181E4. Шаг и порядок в точности совпали с DAMOS, сдвиг +206.

| адрес | имя | масштаб | что |
|---|---|---|---|
| 0x193F3 | `KFABAK` | x0.00390625 | доля плёнки, обогащение на разгоне, 0.281…0.473 |
| 0x19432 | `KFAVAK` | x0.00390625 | доля плёнки, обеднение на сбросе, 0.223…0.496 |
| 0x19471 | `KFBAKL` | x0.0625 | фактор обогащения на разгоне, 0.562…8.438 |
| 0x194B0 | `KFVAKL` | x0.0625 | фактор обеднения на сбросе, 0.812…8.438 |

Общая ось 0x181E4, 7 точек: 20, 30, 40, 50, 65, 80, 105. Масштаб не
установлен -- по DAMOS это либо температура x0.75-48, либо обороты x40.

Все четыре читаются гладко и монотонно, что для плёночной модели и
ожидается.

### Поправка: модель всё-таки правили

Раньше я писал, что плёночную модель на этом блоке не калибровал никто.
**Неверно.** Я смотрел на адреса 0x1931E и 0x1939C, полученные
выравниванием, и они читались мусором.

По настоящим адресам видно другое: `KFBAKL` правили **csok, csok v2,
startpower и Xoptim** -- по 19 байт каждый, все одинаково. Подняты строки
6…8, горячий конец оси:

```
сток        строка 6:  2.25 2.19 2.06 1.94 1.88 1.75 1.69
            строки 7-8: 0.69 0.62 0.56 0.56 0.56 0.62 0.62
тюнеры      строка 6:  2.50 2.44 2.38 2.31 2.25 ...
            строки 7-8: 2.38 2.38 2.38 ...
```

То есть переходное обогащение на прогретом моторе увеличено втрое-вчетверо.
Сток, ori_e3, MPower и L не тронуты.

Это, кстати, не отменяет вывод по провалу: startpower эту правку имеет, а
провал на нём, по словам владельца, такой же.

## Что осталось

Блок динамики контура детонации (`DYADS`, `DYAVF`, `KRFTP1..3`,
`FKELDY`, `REFINI`) по-прежнему не найден. Известные ячейки контура
(`KRFKN`, `KRMXN`, `LKRN`, `KRDWSN`, `TMKR`) кодом напрямую не читаются
-- значит адреса, полученные выравниванием, неверны, и искать надо от
кода, а не от DAMOS.

Из нового по этой теме -- кодовое слово 0x18FC1 рядом с `NKRUM`:
функция 0x84F5F0 делает `if (NKRUM <= обороты && (CW & 1) == 0) сброс`.

## Контур детонации найден

Метод: перебор базы по всему сегменту с двумя условиями сразу --
**все 33 значения цепочки попадают в свои допуски из DAMOS** И
**все 33 ячейки читаются кодом**. На весь сегмент совпадение оказалось
единственным.

```
0x111C0 (DAMOS)  ->  0x1163B (Kia),  сдвиг +1147
```

Одиннадцать значений совпали с исходной M7.9 байт в байт. Всё читается
осмысленно:

| адрес | имя | значение | что |
|---|---|---|---|
| 0x11640 | `KRFTP1` | 16 | фильтр, норма |
| 0x11641 | `KRFTP2` | 4 | фильтр при динамике оборотов |
| 0x11642 | `KRFTP3` | 4 | фильтр при динамике нагрузки |
| 0x11645 | `REFINI` | 0.9766 В | начальный уровень опоры |
| 0x1164D | `KRDWA` | 3.0° | порог расхождения с картой адаптации |
| 0x1164E | `KRDWKLA` | -1.5° | шаг обучения назад при детонации |
| 0x1164F | `KRDWSA` | 1.5° | шаг обучения вперёд |
| **0x11663** | **`DYADS`** | **-1.5°** | доп. откат за цикл при адаптации динамики |
| **0x11664** | **`DYAFVS`** | **0.75°** | шаг возврата при выходе из динамики |
| 0x11665 | `DYAVF` | 1 | длительность отката |
| 0x11667 | `PZWKRA` | 19.92 % | доля циклов с выводом угла от КД при адаптации |
| 0x11668 | `TMDYNA` | 80.25 °C | порог температуры для адаптации динамики |
| 0x1166B | `DKROKU` | 1200 об/мин | нижний предел для калибровки нуля |

**Ни одна из 33 ячеек не отличается между восемью прошивками.** Динамику
детонации не трогал никто -- этот вывод остаётся.

### Отзываю прежнюю таблицу контура

Запись с `KRFKN` 0x18F05 = -3°, `KRMXN` 0x18F15 = -12°, `LKRN` 0x18F4D и
`KRDWSN` 0x18EA3 **неверна**. Эти ячейки кодом не читаются вовсе, адреса
были получены выравниванием, а правдоподобные значения оказались
совпадением. Кривые контура (`KRFKN`, `KRMXN`, `LKRN`, `KRDWSN`, `TMKR`)
заново не найдены.

Уцелел только `NKRUM` 0x18FC2: он читается кодом по 0x4F5F0, и рядом
кодовое слово 0x18FC1.

## Адсорбер найден

Ключ -- сдвиг района 0x19xxx. Он **+206**, и подтверждён независимо
дважды: на плёночной модели (0x19325 -> 0x193F3) и на блоке диагностики
клапана продувки, который нашёлся автоматически через `tools/blockfind.py`
(0x1989F -> 0x1996D, 46 скаляров, 25 значений совпали с исходной M7.9
байт в байт, 38 ячеек читаются кодом).

С этим сдвигом управление адсорбером ложится ровно: из 31 переменной
**28 в допуске, 26 читаются кодом, 21 совпала с M7.9**.

| адрес | имя | значение | что |
|---|---|---|---|
| 0x1976C | `TMTE` | 39 °C | порог температуры двигателя для продувки |
| 0x19535 | `TATELL` | 0 °C | порог температуры воздуха |
| 0x19537 | `TMSNOGA` | 30 °C | порог для непрерывной продувки |
| 0x197AD | `FTEADMX` | 37.5 | максимум насыщения адсорбера |
| 0x197AF | `FTEHB` | 10 | предел фактора продувки |
| 0x1983F | `KFQTE` | карта | скорость нарастания и спада продувки |
| 0x197BC | `KFFTEAN` | карта | ограничение продувки |
| 0x198AD | `ZBTEML` | 0.311 1/с | скорость адаптации насыщения |
| 0x19914 | `ETAZWTEN` | 40 % | мин. КПД угла для диагностики CPV |
| 0x198AB/AC | `KHCTEMN`/`KHCTEMX` | 3.75 / 1.25 | границы концентрации HC в продувке |

Ни одна из них не отличается между восемью прошивками.

**Отзываю прежние адреса** `TMTE` 0x196D1, `FVERMN` 0x11580 и `FQTEFR`
0x1BD74: они были получены выравниванием. В частности, утверждение, что
`TMTE` различается по прошивкам (27.75 / 34.5 / 48 °C), **неверно** --
по настоящему адресу там везде 39 °C.

## Инструмент

`tools/blockfind.py` -- поиск блоков скаляров по двум условиям сразу:
все значения цепочки в допусках DAMOS И достаточная доля ячеек читается
кодом. Принимается только единственное совпадение на весь сегмент.
На этих данных метод даёт мало блоков (два), но каждый -- надёжный.

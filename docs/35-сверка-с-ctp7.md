# Сверка с ChipTuningPRO 7

Владелец выгрузил из CTP7 калибровки прошивки MPower в `.cte`, внутренний
формат CTP7. Кроме того, он поправил в CTP7 одиннадцать одиночных величин и
записал, что именно менял. Всё лежит в `firmware/ctp7/`:

| файл | что это |
|---|---|
| `FBH3ID60-E2_Mod_by_Mpower.bin.cte` | экспорт CTP7: 71 таблица |
| `FBH3ID60-E2_Mod_by_Mpower_test.bin` | прошивка после правок в CTP7 |
| `v1.txt` | список правок, словами владельца |
| `ctematch.json` | итог сверки, по таблице на строку |

Это проверка со стороны. CTP7 не знает ни нашего дамоса, ни моего
выравнивания, ни разбора кода. Если его таблица по значениям и осям совпала
с нашей картой, место и смысл подтверждены независимо от нас.

## Формат .cte

Текст в кодировке cp1251, по устройству похож на INI:

```
[66613309]            ; хеш таблицы
Name=Базовый УОЗ
X1Z1=15,75            ; значение в физических единицах, запятая -- разделитель
...
QX1=680               ; точки первой оси (строки)
QZ1=9,75              ; точки второй оси (подряд)
Const=7900            ; у одиночной величины
```

Адресов в нём нет, но есть значения и оси. Прошивка, из которой сделан
экспорт, у нас тоже есть. Поэтому каждую таблицу можно найти среди наших
карт по содержимому. Этим занимается `tools/ctematch.py`:

```
python3 tools/ctematch.py --bin firmware/ctp7/FBH3ID60-E2_Mod_by_Mpower_test.bin \
    --base firmware/FBH3ID60_mpower.bin \
    firmware/ctp7/FBH3ID60-E2_Mod_by_Mpower.bin.cte --json firmware/ctp7/ctematch.json
```

Правила сопоставления подобраны после двух ложных находок, и обе
закреплены в `tests/test_ctp7.py`:

* **Допуск абсолютный**, не больше полшага квантования и не больше точности,
  с которой CTP7 печатает числа. Относительный допуск у осей оборотов (×40)
  выходил больше единицы, и «коэффициент холодного пуска» прилипал к оси.
  Полшага при множителе 1 — это 0.5, и «макс. богатая смесь» 0.703 прилипала
  к битовому полю, равному 1.
* **Одиночную величину и таблицу из одинаковых чисел по значению опознать
  нельзя**: число 201 найдётся где угодно. Такие опознаются только **по
  правке** (ключ `--base`): из совпавших по значению кандидатов годится тот,
  чьи байты отличаются от прошивки до правки. Если подставить вместо «до»
  ту же прошивку, по правке не опознаётся ничего, и тест это проверяет.
* **Обратная величина.** Коэффициент фильтра момента CTP7 показывает как
  постоянную времени, τ = 2.55 / байт. Такое совпадение печатается
  отдельно, и только для неоднородных таблиц.

Разница прошивок MPower → test — это ровно правки из `v1.txt` плюс
контрольные суммы в 0x1FC68..0x1FC8E. Больше ничего.

## Итог: 51 из 71

| как | сколько |
|---|---|
| совпали значения и оси | 37 |
| совпали по правке владельца | 11 |
| совпали как обратная величина (τ = 2.55 / байт) | 3 |
| таблица из одинаковых чисел или одна величина, кандидат есть | 15 |
| из одинаковых чисел, кандидата нет | 5 |

Ни одна таблица CTP7 не легла на место, где у нас записано другое. В
проверке смыслом (`tools/meaning.py`) у таких карт теперь приговор
«подтверждено CTP7». Он, как и ручной разбор, не перекрывает противоречие с
кодом. Противоречий по-прежнему ноль, а карт с доказанным местом или
смыслом в основном A2L стало 447 из 620 (было 419 из 604).

### Совпали значения и оси

`NLLM`, `NFSM`, `WDKSLN`, `KFZW`, `KFZW2`, `KFZWMN`, `KFLBTS`, `KFWEE`,
`KFWEEK`, `ETALAM`, `ETADZW`, `KFZWOP`, `KFMIOP`, `KFMDS`, `KFDMDFA`,
`KFDMDFAS`, `KFDMDFAU`, `RLLRTMO`, `RLLRUN`, `WDKKOAN_0`, `WDKKOAN_1`,
`WDKKOEN`, плёночная модель `KFABAK`, `KFAVAK`, `KFBAKL`, `KFVAKL`,
`CURVE_19515` и новые записи из раздела ниже.

У `NLLM`, `NFSM` и `ETADZW` адрес раньше держал код, а имя пришло
выравниванием и доверия не заслуживало. Теперь его подтвердил CTP7, и
генератор повышает им достоверность («ИМЯ ПОДТВЕРЖДЕНО CTP7» в отчёте).

показывает именно их.

## Новые записи

Каждая новая запись поставлена по коду, а не по CTP7. CTP7 дал смысл и
масштаб, а адрес и вход взяты из инструкции, которая эту запись читает.
Раздел профиля — `ctp7_confirmed`.

| имя | адрес | что | код |
|---|---|---|---|
| `KST_COLD` | 0x116A5 | коэфф. холодного пуска, 12 точек по ТОЖ | `0x00716a`, вход 0x8AB3, @0x851A20 |
| `KST_HOT` | 0x11692 | коэфф. горячего пуска, 6 точек по **Твозд** | `0x00716a`, вход 0x8AB9, @0x85199E |
| `KST_HOT_MUL` | 0x116C0 | множитель горячего пуска 6×6 | `0x007a94`, входы 0x8A00, 0x8AB9 |
| `KST_COLD_MUL` | 0x11712 | множитель холодного пуска 12×6 | `0x007a94`, входы 0x8A00, 0x8AB3 |
| `KST_COLD_NMUL` | 0x116EE | множитель холодного пуска по оборотам 4×4 | `0x007312`, входы 0x8AB3, 0xF89E |
| `KST_RESTART` | 0x15F78 | обедняющий коэфф. повторного пуска 4×4 | счётчики 0x15F6A/0x15F6B, @0x8519EE |
| `KF_TI_NONLIN` | 0x1B694 | нелинейность подачи топлива 16×16, слова | счётчики 0x1B662/0x1B663, @0x855178 |

| `HFM_LIN_OFS` | 0x15660 | смещение тарировки | `cmp`/`sub`, @0x842CA8 |

Три безымянные находки сканера (`MAP_129_1168B_6`, `MAP_130_11698_12`,
`MAP_131_116B2_6x6`) лежали по верным адресам, но с масштабом 1. Теперь
это `KST_HOT`, `KST_COLD`, `KST_HOT_MUL`.

`CURVE_19515` оказалась **порогом дросселя для включения адаптации**
(0.390625 %/бит, 50.8..60.2 %). Подпись «кривая адсорбера» была догадкой по
соседству. Код читает эту кривую в той же процедуре, что и порог
температуры адаптации 0x11911.

Порядок режимов вентилятора 1–4 взят по адресам. Значения 94.5, 100.5,
100.5 и 114.75 совпадают с CTP7 в том же порядке, но правился только режим 5,
поэтому 2 и 3 по значению неразличимы.

## Что было неверно у нас

**1. Плёночная модель читалась поперёк.** У `KFABAK`, `KFAVAK`, `KFBAKL` и
`KFVAKL` адреса были верны, но в профиле стояло `rows: 9, cols: 7` в
буквальном смысле, а генератор понимает `rows` как число столбцов. Карты
выходили «9 подряд на 7 строк». По байтам видно обратное:

```
0x193F3:  79 79 77 72 6D 6A 68 | 78 78 75 70 6C 69 ...
```

Семь плавных значений, скачок, снова семь. Подряд лежат 7 точек по
оборотам: это заголовок 0x181E4, который получает `0x833FFC`, ×40 = 800 …
4200. Строки — 9 точек температуры ОЖ (ось 0x18273, индекс 0x90AA от
0x8AB4). Теперь у карт настоящие оси. Тест проверяет первую строку, и на
старом описании он падает: там строка `…104, 120, 120` со скачком посередине.

**2. Оси-индексы там, где оси известны.** `KFWEE`/`KFWEEK` (подряд обороты
0x19078, строки нагрузка 0x19081, код @0x85167C), `ETALAM` (лямбда
0.648..1.102, 0x10515) и `KFDMDFA*` (подряд обороты 0x181DD, код
0x83BCC2..) показывались по номеру точки. У `KFDMDFA*` строки так и остались
номером: у CTP7 там 0..5, а величина не установлена.

**3. Отозваны две записи дамоса:**

* `MSNTATE` 0x15F6D — словная кривая по **нечётному** адресу, а на C167
  слово так не читается. На этом месте код берёт байты 0x15F6A и 0x15F6B
  как счётчики, дальше идут две оси и карта `KST_RESTART`. Все её 16 значений
  совпали с CTP7.
* `KFAGRS` 0x1171F — одна «карта 12×16» поверх нескольких объектов. Она
  начинается внутри `KST_COLD_MUL` (все 72 значения совпали с CTP7), дальше
  идут ось на 0x1175A, три кривые, которые код читает по отдельности, и
  заголовок 0x11793 следующей карты. К тому же это рециркуляция ОГ, которой
  на моторе нет.

## Где ошибается CTP7

**Ось нагрузки `KFZW`/`KFZW2`.** Значения обеих карт совпали все, а ось
нагрузки у CTP7 кончается на 90 %, у нас на 99.75 %. В калибровке рядом
лежат две оси по 12 точек, и они отличаются только последней точкой:

| ось | последняя точка | кто читает |
|---|---|---|
| 0x10157 | 99.75 % | индекс 0x90A2 — его берёт `KFZW` (0x83E3D2) |
| 0x1014A | 90 % | индекс 0x90A0 — другая группа карт, таблица указателей 0x1290E (0x8520B8) |

CTP7 подписал `KFZW` соседней осью. Значения от этого не меняются, но при
правке последнего столбца в CTP7 надо помнить, что на деле он отвечает за
нагрузку 99.75 %, а не 90 %.

## Что осталось

Пятнадцать таблиц из одинаковых чисел или одиночных величин, у которых
есть наш кандидат. По значению их не различить, а одна правка в CTP7 решит
каждую:

| CTP7 | наш кандидат |
|---|---|
| Порог по дросселю для режима полной нагрузки / 2 | `WDKVLN_0` / `WDKVLN_1` |
| Состав смеси в режиме полной мощности / 2 | `KLLAMFA_0` / `KLLAMFA_1` |
| Минимальный расчётный УОЗ | `KFZWMS` |
| Мин. открытие дросселя, обеспечивающее макс. наполнение | `WDKUGDN` |
| Состав смеси на частичных нагрузках | `KFLF` |
| Макс. бедная смесь | `CURVE_19509` |
| Коррекция фазы впрыска | `WEEM` |
| Пороги ТОЖ вентилятора, режимы 1–4 | `TMOT_FAN1..4` (по порядку) |

Пять таблиц CTP7 у нас не найдены: «состав смеси при прогреве»,
«коррекция смеси при неактивном лямбда-регулировании», «множитель корр.
ALF», «пороги включения обогащения/обеднения» (±75). Все они из одинаковых
чисел (1.000, 0.992, 0/1, ±75), поэтому найти их можно только правкой.

Ещё три кодовых слова рядом с `LS_CONFIG` правят все прошивки «E2»
(csok, startpower, Xoptim), но не MPower: 0x10021 (2 → 0), 0x10024 (6 → 0)
и 0x10026 (4 → 0). Заодно они ставят и `LS_CONFIG` 3 → 1. 0x10024 у нас
описан как `CWMDAPP` (имя из дамоса), а 0x10021 и 0x10026 не описаны. Код
читает их так же, как 0x10022, проверками битов (0x8284EE.., 0x8285C4,
0x82860C..). Скорее всего, это выключение диагностики катализатора вместе
с задним зондом, но CTP7 их не показывает, и смысл не подтверждён. Раньше эти байты прятались в «области идентификации»
`tools/coverage.py`. Теперь пропуск кончается на 0x10020, и такие правки
видны как непокрытые.

# Топливные карты по коду

Искал по коду то, чем в этой прошивке задаётся топливо. Нашлось больше,
чем ожидал, и две записи в профиле пришлось исправить.

## Почему топливо до сих пор было слепой зоной

Половина калибровки лежит выше `0x18000`, и указатель туда кладётся
**парой**: смещение в `r12`, номер страницы в `r13`.

```
855B5A   mov   r12, #0x1636      ; KFLBTS
855B5E   mov   r13, #0x206       ; страница
855B62   mov   r14, #0x1f7       ; ось SNM16GKUB
855B66   mov   r15, #0x206
855B6E   calls 0x833FFC
```

`tools/mapxref.py` про пару не знал и считал смещение `0x1636` адресом
`0x11636` — то есть чужими байтами. Поэтому весь топливный блок `0x19xxx`
для поиска по коду был невидим, и в профиле стояло «ссылок из кода нет» у
`KRKTE` и у кривых обогащения.

Теперь инструмент разбирает страницу, и картина меняется не числом, а
адресами. Всего карт по коду было 434, стало 425 — но **выше `0x18000`
было 32, стало 258**. Из 238 записей, исчезнувших со старых адресов, 227
просто **переехали на настоящие**: `0x10194` оказался `0x18194`, и так
далее. Ещё 229 адресов не находились вовсе.

## Кривые, которые правят все тюнеры

Две кривые по шесть точек на `0x1955B` и `0x19568`. Прямого указателя на
них в коде нет — и не было: они читаются **через таблицу указателей**.

```
8551CA   movbz r4, 0xf87a          ; вариант, 0 или 1
8551CE   shl   r4, #0x2            ; запись таблицы -- четыре байта
8551D0   mov   r12, [r4+#0x616a]   ; смещение кривой
8551D4   mov   r13, [r4+#0x616c]   ; страница 0x206
8551D8   movbz r14, 0xf89e         ; ОБОРОТЫ
8551DC   calls 0x833a00            ; интерполяция
8551E0   shl   r4, #0x5            ; 128 -> 0x1000 = 1.000
8551E2   mov   0x9880, r4
```

Таблица лежит в самой калибровке:

```
1616A  155B  1616C  0206      ; кривая 0
1616E  1568  16170  0206      ; кривая 1
```

### Поправка: ось не температурная, а по оборотам

В профиле у этих кривых стояла температурная ось: сырые `37 62 87 112
137 162` при `0.75 −48` дают −20.25…73.5 °C. Выглядело правдоподобно, и
поэтому не проверялось.

Код решает вопрос однозначно: на вход подаётся `0xF89E`, а это **обороты
делить на 40**. Те же сырые числа при множителе 40 дают ровный ряд

```
1480  2480  3480  4480  5480  6480  об/мин
```

Значит правка тюнеров обогащает **не на холодном моторе, а во всём
диапазоне оборотов**. Это меняет смысл того, что они сделали, а не только
подпись.

### Куда результат идёт

```
85333E   mov  r4, 0x9880
853342   cmp  r4, 0x98a2
853346   jmpr cc_NC, ...           ; r8 = min(0x9880, 0x98A2)
```

Минимум — потому что **меньше значит богаче**. Дальше на `0x853426`
результат ещё раз минимизируется с `0x97CA`, `0x9428`, `0x94AA` и ложится
в `0x981E`, откуда идёт в заданную лямбду `0x9818` / `0x8A16`. По
умолчанию `0x9880 = 0x1000` (`0x85519A`), то есть «ничего не прошу».

Сток: 128 во всех двенадцати точках — ровно 1.000, запроса нет.
csok: 116…110 → **0.906…0.859**.

> **Поправка, `docs/33`.** Здесь я написал «во всём диапазоне» и не
> проверил, при каком условии кривая вообще читается. Читается она
> **только на полной нагрузке** — на `0x8551A4` стоит `jnb 0xfd48.11`,
> и без этого признака запрос равен ровно 1.000. Это не «лямбда по
> оборотам», это **обогащение полной нагрузки**, у него и имя есть:
> `KLLAMFA`. Разбор цепочки целиком — в `docs/33`.

## Поправка: настоящий адрес KRKTE

`KRKTE` — постоянная форсунки, на неё умножается вся подача. В профиле
она стояла на `0x19485`. Этот адрес получен выравниванием чужого дамоса и
попадает **внутрь плёночной карты** `0x19471`…`0x194AF` (7×9, ось
`0x181E4`, читается на `0x8523F8`). Проверка «физика сходится» ничего не
доказывала: она проверяла ЧИСЛО, а не адрес, и любой байт со значением
92 дал бы то же самое.

Настоящий адрес — **`0x1955A`**:

```
85500A   calls 0x834376
855010   mov   r12, r4
855012   extp  0x206, #0x1
855016   movbz r13, 0x155a        ; KRKTE
85501A   calls 0x006a68           ; умножение
85501E   movb  0x8a27, RL4
```

Сырое значение 93, а не 92; физически 0.1655 мс/% вместо 0.1637 —
разница в пределах той же оценки по рабочему объёму.

Побочный итог: ушло одно из четырёх давних перекрытий «подтверждённая
против подтверждённой». `KFBAKL` и `KRKTE` спорили за одни байты именно
потому, что адрес `KRKTE` был неверен.

## Ряд из тридцати записей, подтверждённый целиком

Сдвиг, который вывел `KRKTE` на `0x1955A`, равен **+0xD5**. Он не
подгонялся: на участке дамоса `0x19460`…`0x194A1` **все тридцать записей
подряд** попали в ячейки, которые код действительно читает, каждая в
своём месте.

| имя | адрес | значение | что это |
|---|---|---|---|
| `TATELL` | `0x19535` | 0 °C | порог температуры воздуха для продувки |
| `TMSKLH` | `0x19536` | 80.25 °C | порог короткой начальной фазы регулятора |
| `TMSNOGA` | `0x19537` | 30 °C | порог бесконечной продувки |
| `FBZFRAT` | `0x19538` | 5 точек | вес скорости интегрирования `KFFRAT` |
| `FRAOMN` … `FRAURX` | `0x19543`…`0x1954C` | 0.75 / 1.25 | пределы коррекций frao, frat, frau |
| `NO1`, `NU3` | `0x1954D`, `0x1954F` | 920, 7000 об/мин | границы диапазонов адаптации |
| `NOLRA` | `0x1954E` | 36 | кодовое слово разрешения адаптации |
| `RLO2` … `RLU4` | `0x19550`…`0x19556` | 20…60 % | границы диапазонов по нагрузке |
| `TMFRATMN`, `TMFRATUB` | `0x19557`, `0x19558` | 20.25, 0 °C | пороги температуры для ftklra |
| `CWPKAPP` | `0x19559` | 0 | кодовое слово опорного давления топлива |
| `KRKTE` | `0x1955A` | 0.1655 мс/% | постоянная форсунки |
| `CWLAMBTS` | `0x19575` | 3 | кодовое слово лямбды защиты компонентов |
| `KFFDLBTS` | `0x19576` | 12×16 | разрешение лямбды защиты компонентов |

Двадцать восемь читаются напрямую (`extp 0x206` и следом `cmpb`/`movbz`),
две — карты, и читаются указателем: `FBZFRAT` на `0x85470E`, `KFFDLBTS`
на `0x855C44`.

Две записи ряда — `TATELL` и `TMSNOGA` — уже стояли в профиле, найденные
совсем другим путём (блок адсорбера). Они сошлись по адресу, и это
закрепляет сдвиг независимо от дамоса.

**Осторожно со сдвигом.** По области он не постоянный: у блока
диагностики адсорбера +0xCE, здесь +0xD5. Поэтому каждая запись проверена
отдельно ссылкой из кода, а не взята по одному общему сдвигу.

## Что подтвердилось без изменений

| карта | адрес | код |
|---|---|---|
| `KFLF` — лямбда частичных нагрузок | заголовок `0x190CE`, данные `0x190EC` | `0x8517D0`, входы обороты и `0xF86B` |
| `KFLBTS` — лямбда защиты компонентов | `0x19636`, ось `0x181F7` | `0x855B6E`, результат ×32 → `0x98A4` |
| `KFFDLBTS` — разрешение | `0x19576`, та же ось | `0x855C44` — был «кандидат», стал подтверждённым |
| плёночная модель | `0x193F3`, `0x19432`, `0x19471`, `0x194B0`, ось `0x181E4` | четыре карты 7×9 подряд |

Расхождение «профиль против дамоса» у `KFLF` оказалось мнимым: `0x190CE`
— адрес заголовка, `0x190EC` — адрес данных, и `0x190CE + 2 + 16 + 12 =
0x190EC`. Обе записи верны, просто про разное.

## Чего в этой прошивке нет

Топливной карты в привычном виде — таблицы миллисекунд или наполнения —
здесь по-прежнему нет, и поиск по коду это подтвердил: ни одна карта не
отдаёт время впрыска. Впрыск считается из воздушной модели, а карты
задают только **цель по лямбде**. Правят топливо тремя вещами:

1. кривые запроса лямбды по оборотам `0x1955B` / `0x19568`;
2. `KFLBTS` — лямбда защиты компонентов;
3. `KRKTE` — постоянная форсунки (её не трогал никто).

## Мера качества, не зависящая от чужого мнения

`tools/coverage.py` считает единственную проверку, которая не опирается ни
на дамос, ни на чужой модуль: **всё, что человек правил в чужой прошивке,
он правил осмысленно** — значит по этому адресу стоит настоящая
калибровка. Если наш A2L её не знает, это дыра, и видно, где именно.

```
ИТОГО: 11680 правленых байт в одиннадцати прошивках,
       в известных картах 11599 (99.3 %)
```

Обратное неверно, и это надо помнить: попадание в карту не доказывает,
что у карты верное ИМЯ. Проверяется покрытие, а не подписи.

Первое, что проверка нашла, — **самого правленого места во всей прошивке
в описании не было вовсе**. Кривые `0x19562` и `0x1956F` лежали в профиле
свободной формой, которую сборщик A2L не читает. Теперь они там есть, под
нашими именами `CURVE_1955B` и `CURVE_19568`: заводского имени нет, и
выдумывать боschевское нельзя — его начнут искать в дамосах.

Осталось 163 неопознанных байта в 29 участках. Крупнейшие:

| участок | байт | кто правил |
|---|---|---|
| `0x14E64`…`0x14E81` | 30 | почти все |
| `0x1655A`, `0x165E2`, `0x16632` | по 16 | только startpower |
| `0x11DA1`…`0x11DD5` | 16 | многие, россыпью |
| `0x19520`…`0x19529` | 10 | Spectra mod |
